핵심 영역
데이터 소멸 및 보존 정책, 동시성 제어 모델, 불변식 검증 위치, 관찰 상태 계약

본 문서는 DESIGN.md 스토리지 계층 리팩토링 과정에서 개정된 핵심 아키텍처 계약(Contract) 및 데이터 보존/동시성 모델의 변경 사항을 명시한다. 파일-데이터베이스 동기화 시 데이터 영속성을 보장하기 위한 정책 전환과, 후속 단계(U7/U8)에서 요구되는 아키텍처 의사결정 항목을 기술한다.

1. 핵심 계약 변경 사항 (Core Contract Shifts)

계약 변경 1: 고아 행(Orphan Row) 정책 전환 (Hard Delete → Unbind)

파일 탐색(discover_design_files) 집합에 포함되지 않는 기존 파일 기반 레코드를 처리할 때, 기존의 물리 행 삭제(Hard Delete) 방식을 파일 소스 연결 해제(Unbind) 방식으로 전면 개정하였다.

배경 및 위험 요소

초기 설계(KTD9)는 "DB는 소멸 가능한 캐시이며 파일이 복구 원본"이라는 전제를 채택하여 파일 부재 시 DB 행을 삭제하였다. 그러나 design_systems.id는 파일 재인덱싱으로 복구할 수 없는 하위 런타임 데이터(프로토타입 실행, 후보군, 내보내기 이력 등)의 외래 키(Foreign Key) 루트로 동작하므로, 행 삭제 시 광범위한 연쇄 데이터 손실(Cascade Loss)이 발생하였다. 

# crud/crud_design_system.py
- statement = sa.delete(DesignSystem).where(
-     DesignSystem.source_path.is_not(None),
-     DesignSystem.source_root == source_root,
-     DesignSystem.slug.not_in(keep_slugs),
- )
+ statement = (
+     sa.update(DesignSystem)
+     .where(
+         DesignSystem.source_path.is_not(None),
+         DesignSystem.source_root == source_root,
+         DesignSystem.slug.not_in(keep_slugs),
+     )
+     .values(
+         source_path=None, source_root=None,
+         source_digest=None, source_mtime_ns=None,
+         source_size=None, synced_at=None,
+     )
+ )

# service/design_system_service.py — index_all
+ root = Path(repo_root).resolve()
+ if not root.is_dir():
+     raise SourceRootNotFoundError(...)

1. 연산 유형 전환 (DELETE → UPDATE)조회 조건(WHERE)은 동일하게 유지하되, 대상 행의 파일 연결 메타데이터 컬럼을 None으로 초기화하는 UPDATE 구문으로 전환함.

2. 메서드 명세 변경메서드 식별자를 delete_orphan_sources에서 unbind_orphan_sources로 수정하여 실제 연산 의도를 정확히 반영함.

3. 소스 루트 사전 검증 (Root Guard) 추가존재하지 않는 디렉터리 경로 전달 시 파일 탐색기가 빈 목록([])을 반환하여 정상 파일들의 연결이 오해제되는 사고를 차단하기 위해 SourceRootNotFoundError 검증 가드를 신설함.

관련 문서 개정: 스토리지 설계 결정서의 KTD11("고아 레코드 하드 삭제") 명세를 "소스 메타데이터 연결 해제(Unbind)"로 공식 개정하였다.

계약 변경 2: 동시성 제어 모델 고도화 (전역 Lock → AsyncReadWriteLock)

전역 단일 뮤텍스(_index_lock: asyncio.Lock)로 인해 발생하던 무관한 슬러그 간 조회 직렬화 병목을 해소하기 위해, 판독(Read)과 기록(Write)을 분리하는 AsyncReadWriteLock을 도입하였다.

배경 및 문제점

기존 구조에서는 index_all(), get(), apply_token_patch()가 모두 전역 잠금을 획득하도록 강제되어, 서로 다른 슬러그에 대한 순수 조회 요청 간에도 상호 배제가 발생하였다. 이로 인해 슬러그별 세분화 잠금(_lock_for(slug))이 실질적으로 무력화되는 구조적 한계가 존재하였다.

검증 체계: 서로 다른 슬러그 간의 비차단 조회를 보증하는 동시성 회귀 테스트(test_queries_on_different_slugs_do_not_serialize)를 추가하여 동시 조회 성능을 보증함.

계약 변경 3: 불변식 검증 위치의 실효적 재배치

토큰의 상위 시스템 재할당(Reparenting)을 방지하는 불변식 검사 위치를, 실행 도달이 불가능하던 데이터클래스 생성자에서 CRUD DAO의 데이터 교체 진입점(crud_design_token.replace)으로 이전하였다. 

# AS-IS: storage/design_system_store.py (검증 불가)
design_token = DesignToken(
    design_system_id,
    token.tier, token.token_path, token.value,
)
if design_token.design_system_id != design_system_id:
    raise TokenReparentingError(...) # 항상 False로 도달 불가

# TO-BE: crud/crud_design_token.py — replace() (실효 검증)
reparented = [
    token for token in token_rows
    if token.design_system_id != design_system_id
]
if reparented:
    raise TokenReparentingError(...)

# 사전 검증 통과 후에만 기존 토큰 삭제 및 교체 실행
await self.delete_model_by_column(...)

1. 검증 실효성 확보DesignToken 모델은 필드 단순 대입 구조이므로 생성 직후 불일치 검사가 성립하지 않았음. 실제 파라미터로 전달된 토큰 엔티티 집합 전체의 소유권 ID를 DAO 레벨에서 검사하도록 수정함.

2. 트랜잭션 안전성 보장불변식 검증을 기존 레코드 삭제 구문(delete_model_by_column)보다 앞단에 배치하여, 불일치 데이터 유입 시 기존 토큰이 유실되지 않고 안전하게 롤백되도록 보장함.

계약 변경 4: 관찰 상태 열거형(Enum)의 완전성 및 예외 처리 격리

소스 관찰자(observe_design_source)가 파일 시스템 상태 확인(stat)과 파일 판독(read) 사이의 경쟁 조건(Race Condition)으로 인해 파일 누락 예외를 외부로 전파하던 결함을 수정하였다.

  • 계약 보장: 파일 소멸 시 MissingSourceFileError를 포착하여 정상적인 DesignSourceStatus.MISSING 상태값으로 반환하도록 계약을 완전화함.
  • 역할 분리: 저장소 어댑터는 사실 정보(Enum 상태)만 보고하고, 서비스 계층이 이에 대한 정책 판단(조회 시 stale=True 반환, 패치 요청 시 수정 거부)을 전담하도록 책임을 명확히 분리함.

2. 현재 계층 아키텍처 구조 (Architecture Layering)

3. 후속 아키텍처 의사결정 항목 (Key Architectural Decisions)

스토리지 계약 개정에 따라 후속 마일스톤(U7 어댑터 연동 및 U8 CLI 확장) 진입 전 확정되어야 할 설계 결정 사항을 기술한다.

Decision C: replace()의 다중 origin 토큰 보호 정책P1 - Pre-U7 Critical

문제 정의: design_token_dao.replace는 특정 시스템의 토큰을 전면 삭제 후 재삽입한다. 현재 origin 컬럼은 design_md | admin_ui | agent를 허용하나, replace는 origin 구분 없이 전체를 삭제한다. 이로 인해 파일 변경에 따른 동기화(get() 재인덱싱) 시 admin_ui나 agent가 등록한 토큰이 함께 삭제될 위험이 있다.

현 상태: 현재는 design_md 단일 origin만 사용 중이므로 즉각적인 데이터 손실은 없으나, 관리 UI(R18) 및 에이전트 토큰 연동 시 결함으로 발현된다.

설계 대안:

  • 대안 1 (Origin 스코프 분리): replace 대상을 origin='design_md'로 한정하고 타 origin 토큰은 보존함. 단, 동일 token_path 충돌 시 캐스케이드 우선순위(R1) 규칙이 정의되어야 함.
  • 대안 2 (Write-Through 단일 원천 원칙): 파일(DESIGN.md)을 단일 진실 원천으로 확정하고, UI/에이전트 수정은 반드시 파일에 선반영(Write-through)되도록 규정함.
[권고안]: 대안 2 채택
초기 단계에서는 KTD9("파일이 복구 원본") 원칙에 따라 파일 Write-through 방식을 기본 계약으로 확정하고, 다중 원천 오버라이드 요구사항(R1)이 구체화될 때 대안 1의 병합 규칙을 추가 도입함.

Decision A: 바인딩 해제(Unbound) 레코드의 수명주기 및 정리 정책P2 - Lifecycle Policy

문제 정의: 하드 삭제가 제거됨에 따라 파일이 삭제된 시스템 레코드는 DB 전용 행(source_path IS NULL)으로 영구 유지된다. 또한 파생 시스템(Derived System, R22)과 파일 연결이 끊긴 고아 레코드가 동일한 source_path IS NULL 상태를 공유하여 식별 모호성이 발생한다.

설계 대안:

  • 대안 1: 현재 상태 유지 (슬러그 단위로만 증가하므로 저장 용량 부담 미미).
  • 대안 2: U8 CLI에 명시적 정리 명령(protokflow index --prune)을 도입하여 명시적 요청 시에만 안전하게 행을 삭제함.
  • 대안 3: unbound_at 타임스탬프 컬럼을 신설하여 고아 레코드와 파생 시스템을 명시적으로 구분함.
[권고안]: 대안 2 + 대안 3 점진적 적용
자동 삭제를 배제하는 안전 원칙을 유지하되 U8에서 명시적 --prune 명령을 제공하고, 파생 시스템(R22) 구현 시점에 unbound_at 또는 명시적 system_type 필드를 스키마에 추가함.

Decision B: CRUD 계층의 불변식 사전조건 검증 책임 범위P2 - Architecture Scope

문제 정의: KTD5는 "crud/는 SQLAlchemy 문장만 소유하고 트랜잭션을 커밋하지 않는다"로 규정되어 있으나, 신규 추가된 토큰 소유권 검증 로직은 단순 SQL 문장을 넘어선 엔티티 무결성 검증을 포함한다.

[권고안]: KTD5 명세 범위의 현실적 정규화
"crud/는 SQLAlchemy 문장과 해당 파괴적 문장(전체 삭제 등) 실행에 필수적인 즉시 사전조건(Preconditions) 검사를 소유한다"로 정의를 정밀화하여, DAO 직접 호출 시에도 데이터 정합성을 항시 보장함.

Decision D: 동일 토큰 동시 패치 정책 (Last-Writer-Wins 확정)P3 - Concurrency Contract

문제 정의: apply_token_patch는 버전 파라미터를 받지 않으며, KTD6에 따라 패치 성공 시 예외 없이 반영된다. 동일 토큰 경로(token_path)에 대한 동시 요청 시 마지막 쓰기가 이전 쓰기를 덮어쓰는(Last-Writer-Wins) 구조를 취한다.

[권고안]: Last-Writer-Wins(LWW) 공식 계약 확정
프로토타이핑 도구의 특성상 복잡한 낙관적 락(Optimistic Locking) 대신 LWW 정책을 공식 계약으로 문서화하고, 해당 동작을 명시적으로 검증하는 동시성 테스트를 추가 유지함.

Decision E: AsyncReadWriteLock 공용 모듈 위치 및 거버넌스P3 - Utility Governance

문제 정의: 신규 작성된 backend/common/rwlock.py는 현재 서비스 계층 한 곳에서만 참조되고 있어 공용 유틸리티로서의 분리 필요성에 대한 검토가 필요함.

[권고안]: backend/common/rwlock.py 독립 유지
잠금 동기화 프리미티브는 서비스 비즈니스 로직과 분리되어 자체 단위 테스트(5개 케이스)로 엄격히 검증되는 것이 유지보수성 및 안정성 측면에서 유리함.

4. 시스템 구현 및 운영 참고 사항 (Implementation Notes)

  • 슬러그별 잠금 딕셔너리 메모리 수명: _locks 딕셔너리는 항목을 별도 회수(Evict)하지 않으나, 고유 슬러그 수에 의해서만 한정(Bounded)되므로 일반적인 런타임 환경에서 무해함.
  • 배치 인덱싱 원자성: index_all은 디렉터리 내 단 하나의 DESIGN.md 파일이라도 파싱 실패할 경우 배치 전체를 즉시 중단(All-or-Nothing)하는 정책을 유지함.
  • 다중 루트 슬러그 매핑: 슬러그는 시스템 전역 유일 식별자이나 source_root는 행별로 관리됨. 동일 슬러그를 가진 파일이 서로 다른 루트에 존재할 경우 상호 재바인딩이 발생하므로 프로젝트 루트 설정 관리에 유의해야 함.
  • 비정상 파일 예외 처리: 파일 내용이 손상된 경우 get()은 stale=True로 격하하지 않고 파싱 예외를 즉시 발생시켜 비정상 상태의 은폐를 방지함.

5. 결론 및 요약

이번 스토리지 계층 계약 개정은 "연쇄적 데이터 파괴 차단(Unbind 도입), 불필요한 조회 직렬화 제거(AsyncReadWriteLock 적용), 실효적 불변식 검증 배치(CRUD DAO 가드)"를 통해 데이터 영속성과 동시성 처리 성능을 동시에 확립하였다. 향후 U7 어댑터 계층 구현 시 replace()의 다중 origin 처리 계약(Decision C)을 우선 확정하고 구현을 진행한다.
