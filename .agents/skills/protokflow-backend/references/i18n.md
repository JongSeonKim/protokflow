# Internationalization (i18n) Mechanism

How locale resolution works internally: the `t()` function, the `Accept-Language` middleware,
and the request/task-isolated `current_language` primitive. For raising *localized business errors*
(`t('error.<domain>.<key>')` vs `CustomErrorCode`), see `error-localization.md`.

## The moving parts

- **`I18n` singleton** (`backend/common/i18n.py`): loads locale packs at import into
  `i18n.locales` (`backend/locale/ko-KR.yaml`, `en-US.json`) and exposes `t(key, **kwargs)`.
- **`current_language`** — a property backed by a module-level `contextvars.ContextVar`
  (default `settings.I18N_DEFAULT_LANGUAGE`, which is `ko-KR`). Each async context/request
  gets its own isolated value; it is **not** a process-global attribute that leaks across requests.
  Read and write it as `i18n.current_language` — the ContextVar is an implementation detail.
- **`t(key, default=None, **kwargs)`**: resolves `key` against `i18n.locales[current_language]`,
  interpolating `{placeholders}` via `str.format`. An unknown language falls back to the default
  pack; a missing key resolves to the raw dotted key (or `default`).
- **`I18nMiddleware`** (`backend/middleware/i18n_middleware.py`, a Starlette
  `BaseHTTPMiddleware`): maps the request `Accept-Language` header to a locale and sets
  `i18n.current_language` before `await call_next(request)`.

## Resolution order

`Accept-Language` header → `I18nMiddleware` sets `current_language` → endpoint/handler reads
`t(...)` / `current_language`. A request with no header resolves the default (`ko-KR`). Header
mapping is in `get_current_language` (`en`/`en-us` → `en-US`, `ko`/`ko-kr` → `ko-KR`, else the
raw lowercased tag).

## Middleware-to-handler propagation

The locale set by `I18nMiddleware` reaches downstream route handlers and app-level exception
handlers (e.g. `_validation_exception_handler`) — verified on the pinned stack (Starlette 1.0.0 /
anyio 4.13.0), where anyio copies the current context into the task-group child that runs the
endpoint. This is version-sensitive: after a Starlette/anyio upgrade, re-verify a non-default
locale still reaches the handler (regression signal = localized message silently resolving in
`ko-KR`). See `docs/solutions/architecture-patterns/i18n-current-language-contextvar-backing.md`
for the investigation record.

## Reading/writing the locale in code

In request handlers and services, **read** the locale via `i18n.current_language` or just call
`t(...)` — never hardcode a pack. The only production **writer** is `I18nMiddleware`; do not set
`current_language` elsewhere in production code.

The ContextVar gives async-context isolation, but note the middleware sets a *shared* per-context
value, not a request-scoped primitive that is guaranteed to reset between requests. True per-request
async isolation on top of this primitive is a deliberate follow-up, not the current behavior.
